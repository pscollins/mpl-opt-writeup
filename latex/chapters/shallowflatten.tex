The action of the \texttt{ShallowFlatten} pass is to eliminate array-of-tuple
types from the program, converting them to either a single flat array or a tuple
of arrays. It is intended to be a more ``agressive'' extension of the existing
\texttt{DeepFlatten} pass, extending to cases where temporary tuple allocations
are required.

\section{Motivation}
As outlined in \cref{sec:background_deep_flatten}, the MLton default
array-of-pointers is \hl{disasterous} from the perspective of cache-efficiency,
introducing a load to an unpredictable, likely-cold heap location on every
element access. The existing remedy to this problem is the \texttt{DeepFlatten}
pass, but \texttt{DeepFlatten} only supports the case where the transformation
is completely ``free,'' introducing zero new \texttt{tuple} allocations. This
seems to be an inversion of priorities: \texttt{ShallowFlatten} takes the
opposite approach, inserting temporary \texttt{tuple} objects for all operations
into or out of containers and relying on later optimization passes to eliminate
them.

What alternatives to the mechanism used by \texttt{DeepFlatten} exist? Given a
container-of-\texttt{tuple} type in the source language, what transformations
could we apply in order to guarantee that the generated C contains no
container-of-pointer types? How can we generalize the \texttt{Flatten}
transformation to apply to containers?

For one possible strategy, consider the action of \texttt{Flatten} on function
arguments in the \texttt{SSA} representation: it dissolves the association
between conjoined \texttt{tuple} elements by introducing a new name for each
member. Mapping this on to arrays, we can, likewise, dissolve the association
between \texttt{tuple} members by providing a distinct (array-valued) name for
each element of the \texttt{tuple}. See \cref{fig:ssa_flatten_vs_soa} for an
example.

For another strategy, consider the action of \texttt{Flatten} on inter-chunk
function calls in the generated C: rather than copying a pointer into the stack,
we copy the elements of the pointed-to object into the stack themselves. Mapping
this on to arrays, we can, likewise, eliminate pointers by copying the elements
of the pointed-to object directly into the array's backing storage. See
\cref{fig:ssa_flatten_vs_aos} for an example. This most-closely matches the
existing \texttt{DeepFlatten} transformation.

Speaking somewhat loosely, these two choices of strategies correspond to the
familiar struct-of-arrays (SoA) vs array-of-structs (AoS) layouts. The AoS
layout is the natural default for a C++ programmer, where a composite type is
embedded directly into the container (\cref{fig:cpp_aos_diagram}). The SoA
layout is the natural default for SIMD programming, since it makes it simple to
load contiguous chunks of data into SIMD registers (\cref{fig:cpp_soa_diagram}).
The MLton default array-of-pointers layout (\cref{fig:aop_example}) lacks a name
in standard performance-engineering parlance -- we will refer to it here as
``AoP'' for simplicity.

Bridging the gap consists, broadly, in inserting ``pack'' and ``unpack''
sequences as necessary around all \texttt{prim} operations that access container
types, replacing the AoP container type with its AoS/SoA equivalent, and
rewriting the container \texttt{prim}s appropriately
(\cref{fig:pack_unpack_example}). This allows us to preserve all of the
pre-existing names and (non-container) types in the consuming code, at the cost
of potentially-unnecessary tuple allocations. In order to offset this effect,
the \texttt{ShallowFlatten} pass runs relatively early in the \texttt{SSA} pass
pipeline -- directly before the regular \texttt{Flatten} pass -- which allows us
to reuse the existing mechanisms for \texttt{tuple}-elimination to the greatest
extent possible.

This choice comes with a tradeoff, however: in the \texttt{SSA} representation,
memory layouts are abstract, and so it is impossible for us to directly express
a notion of ``\texttt{tuple} elements embedded into an array'' that the
\texttt{DeepFlatten} pass produces (depicted in \cref{fig:flatten_generated_c}),
which would be a direct analogue to the traditional C++ AoS layout depicted in
\cref{fig:cpp_aos_diagram}. However, for containers of a uniform type, this
level of control is unnecessary -- we can, for example, simply convert an
length-$n$ \texttt{(int * int)} into an \texttt{int array} of length $2n$. For
the benchmarks explored below, restricting the transformation to tuple elements
with homogoneous types does not sacrifice any performance -- container-of-tuple
types represented in these workloads generally correspond to e.g. 2-$d$ points
in space, which are naturally homogeneous.

While inserting pack/unpack operations allow us to preserve pre-existing names
and types in code that consumes container elements, the types of the containers
themselves must be rewritten in order to reflect the new layouts. Like
\texttt{PreFlatten} (and unlike \texttt{DeepFlatten}), \texttt{ShallowFlatten}
aims to be a simple, purely-local transformation (rather than a complicated
global lattice analysis). Consequently, it is necessary for the pass to
eliminate every single appearance of a flattenable container type -- even those
embedded inside of e.g. \texttt{datatype} definitions or other container types
-- since otherwise we would end up with mismatched types at boundaries where
flattenable containers are embedded inside of other objects. See
\cref{fig:soa_flat_deep_example} for an illustration.

\section{Implementation}
We will formalize the action of the pass in three steps: first, a
``flavor''-independent high level structure, parameterized on a ``flavor''
$\Phi \in \{\texttt{AoS}, \texttt{SoA}\}$; second, we describe the
flavor-dependent transformation on types, and finally the flavor-dependent
transformation on statements.

\hl{TODO: mention the homogeneous tuple restriction in limitaitons
-- say that we could skip it for AoS but it's easier to keep it}

We define the ``\texttt{tuple} width'' of a type $t$ as $w_t(t)$,
where:
\[
w_t(t) =
\begin{cases}
n &: \textrm{if $t$ is of the form $\underbrace{\tau * \cdots * \tau}_{n}$} \\
0 &: \textrm{otherwise}
\end{cases}
\]
We likewise define the ``container width'' of a type $c$ as $w_c(c)$, where:
\[
w_c(c) =
\begin{cases}
w_t(t) &: \textrm{if $c$ is $t$ \texttt{array} or $t$ \texttt{vector}} \\
0 &: \textrm{otherwise}
\end{cases}
\]
In the context of \texttt{ShallowFlatten} We say that a type $\tau$ is
``flattenable'' if:
\[
2 \leq w_c(\tau) \leq W
\]
where $W$ is some user-specified upper bound (selected to maximize performance).

We also partition \texttt{prim}s into ``flattenable'' and ``unflattenable:''
``flattenable'' \texttt{prim}s are those that manipulate \texttt{array}
or \texttt{vector} types; all other \texttt{prim}s are ``unflattenable.''

Then, at a high level, the action of the pass is:
\begin{itemize}

\item Visit all non-\texttt{statement}s; recursively
(i.e. traversing nested types) and iteratively (i.e. repeating until
convergence) transform all \texttt{type}s under the flavor $\Phi$.

\item Visit all \texttt{statement}s: iteratively transform under $\Phi$ until convergence.
For \texttt{statement}s that contain a flattenable \texttt{prim}, this means
rewriting the \texttt{prim} according to $\Phi$; for statements that do not
contain a flattenable \texttt{prim}, it means transforming only \texttt{type}s.

\end{itemize}

See \cref{fig:shallow_flat_toplevel} for a formalization.

\subsection{Type transformation}
The core transformation is to rewrite an array-of-tuple to a tuple-of-array:
\begin{minted}{python}
  (a * b * c * ...) array ->
  a array * b array * c array * ...
\end{minted}
Since there exist constructs that convert the type \texttt{a array} to \texttt{a
  vector} (which is effectively a cast, for which MLTon inserts a copy in order
to prersve the property that \texttt{vector} objects are immutable after
construction), applying the optimization to \texttt{array} requires a either
matching transformation for \texttt{vector}, or a complicated re-un-flattening
in order to construct the contents of the un-flattened \texttt{vector} type.

In this document, we choose the former strategy, rewriting \texttt{vector} types
in addition to \texttt{array} types:
\begin{minted}{python}
  (a * b * c * ...) vector ->
  a vector * b vector * c vector * ...
\end{minted}

Likewise, it is necessary to traverse ``deeply'' inside of types, i.e. we need
to do the transformation:
\begin{minted}{python}
  ((a * b) array * c) ->
  ((a array * b array) * c)
\end{minted}
since, in order to construct an object of type \texttt{(a * b) array * c}, we
need an input object of type \texttt{(a * b) array}, which will be flattened by
the transformation below.

It is similarly necessary to apply the transformation iteratively, i.e. we need:
\begin{minted}{python}
  ((a * b) array * c) array ->
  ((a * b) array) array * c array ->
  (a array array * b array array) * c array
\end{minted}
since in order to construct the original type, we needed to have an object of
type \texttt{(a * b) array} in hand, and this object was transformed into an
\texttt{a array * b array} by the earlier action of the pass.

\subsection{Statement transformation}
The general form of an \texttt{SSA} statement is:
\begin{minted}{python}
  lhs: lhsTy = exp
\end{minted}
where \texttt{lhs} is a variable name, \texttt{lhsTy} is its type, and
\texttt{exp} is an expression.

The transformation on statements is divided into two cases: ``passthrough'' and
``rewrite.'' Every non-\texttt{PrimApp} statement is a ``passthrough''
statement. Taking \texttt{fTy} as the transformation on types above, these cases
are all
\begin{minted}{python}
  lhs: lhsTy = exp ->
  lhs: fTy(lhsTy) = exp
\end{minted}
where \texttt{exp} is some expression that contains no type expressions.

The general form of a \texttt{PrimApp} is:
\begin{minted}{python}
  lhs: lhsTy = prim PrimName[targ1, targ2, ...](arg1, arg2, ...) ->
\end{minted}
where \texttt{PrimName} is the name of a particular primitive operation (e.g.
\texttt{Word32\_add}, \texttt{Word32\_equal}, etc), \texttt{targ1, targ2, ...}
is a sequence of zero or more type arguments, and \texttt{arg1, arg2, ...} is a
sequence of zero or more variable names.


The ``passthrough'' case for \texttt{PrimApp} applies to all \texttt{PrimApp}s
that do not manipulate flattened containers. Its general form is:
\begin{minted}{python}
  lhs: lhsTy = prim PrimName[targ1, targ2, ...](arg1, arg2, ...) ->
  lhs: fTy(lhsTy) = prim PrimName[fTy(targ1), fTy(targ2), ...](arg1, arg2, ...)
\end{minted}
i.e.: leave all non-type portions of the expression unchanged, and transform all
type expressions according to the type transformation above.

The non-``passthrough,'' ``rewrite'' case applies to \texttt{PrimApp}s that
manipulate flattened containers. These transformations differ between the SoA
and AoS cases.

Beginning with the SoA case, the general form of the transformation is ``find
all containers of tuples, rewrite them to be tuples of containers.'' Beginning
with container-creation as an illustrative example, a single step of the
transformation is:
\begin{minted}{python}
  x: (a * b * ...) array = prim Array_alloc[a * b * ...](n) ->
  # Construct per-member arrays
  arr_a: a array = prim Array_alloc[a](n)
  arr_b: b array = prim Array_alloc[b](n)
  ...
  # Bind the tuple-of-arrays to the original name
  x: a array * b array * ... = tuple(arr_a, arr_b, ...)
\end{minted}
and now the other transformations of the pass are responsible for ensuring that
other uses of \texttt{x} in the program use the updated type (e.g. any function
signatures must be rewritten according to \texttt{tTy}, etc).

types, e.g. after one round, we get:
\begin{minted}{python}

we described above, the type transformation will eliminate all ocurrences of
flattenable types in the program. Hence any users of \texttt{a} will fail to
typecheck, and the resulting program is ill-formed. Applying another round of
``rewrite''-flattening to each of the resulting expressions resolves the issue:

  arr_c: c array = prim Array_alloc[a * b](n)
  x: ((a * b) array * c array) = tuple(arr_ab, arr_c)
  ->
  arr_a: a array = prim Array_alloc[a](n)
  arr_b: b array = prim Array_alloc[b](n)
  arr_ab: a array * b array = tuple(arr_a, arr_b)

\section{Formalization}
\label{sec:shallowflatten_formalization}

Following the grammar of the \texttt{SSA} IR in \cref{fig:ssa_grammar}, we
formalize the action of \texttt{ShallowFlatten} on a program $P = D_1 \cdots D_l
\; F_1 \cdots F_m$. The transformation is parameterized by a layout strategy
(SoA or AoS) and a maximum tuple width threshold $W \ge 2$, which together
determine a predicate $\Phi(\tau)$ identifying flattenable element types:
\begin{itemize}
\item Under the SoA strategy, a tuple type $\tau = \tau_1 * \cdots * \tau_k$ is
  flattenable ($\Phi_{\text{SoA}}(\tau)$) whenever its width satisfies $2 \le k
  \le W$. Under the AoS strategy, $\tau$ must additionally be homogeneous
  ($\Phi_{\text{AoS}}(\tau)$), with $\tau_1 = \cdots = \tau_k = \tau_0$,
  \cref{fig:shallowflatten_types}.

\item Every type annotation $\tau$ in the program is rewritten by iterating the
  single-step type transformation $\sembrack{\tau}$ to a fixed point
  $\sembrack{\tau}^*$, converting containers over flattenable tuple types into
  tuples of containers (SoA) or single containers over the homogeneous member
  type (AoS) while traversing deeply into nested composite types,
  \cref{fig:shallowflatten_types}.

\item Top-level non-statement AST constructs (\texttt{datatype} declarations
  $D$, function signatures $F$, and basic block headers $B$) replace all
  embedded type annotations $\tau$ with their fixed-point flattened counterparts
  $\sembrack{\tau}^*$, while control-flow transfers $tr$ contain no type
  annotations and remain unchanged, \cref{fig:shallowflatten_ast_top}.

\item Statements $s$ are rewritten by iterating the single-step statement
  transformation $\sembrack{s}$ to a fixed point $\sembrack{s_1 \cdots s_m}^*$
  within each basic block, \cref{fig:shallowflatten_ast_top}. Non-\texttt{prim}
  statements and \texttt{prim} applications that do not manipulate flattenable
  containers act as passthroughs, updating only their embedded type annotations
  via $\sembrack{\cdot}$, \cref{fig:shallowflatten_passthrough}.

\item Primitive applications on containers with flattenable element types $\tau$
  (drawn from the set of container primitives $\mathcal{P}_{\text{container}}$)
  are expanded into sequences of per-member operations paired with
  \texttt{tuple} pack and \texttt{select} unpack statements under SoA
  (\cref{fig:shallowflatten_prims_soa}) or scaled-index slice operations under
  AoS (\cref{fig:shallowflatten_prims_aos}). Iterating $\sembrack{\cdot}$ to a
  fixed point both expands nested flattenable containers and propagates updated
  types across all newly-emitted statements.
\end{itemize}

\Cref{fig:shallow_flatten_ast,fig:shallow_flatten_prims} make this precise,
writing $\sembrack{\cdot}$ for a single step of the transformation and
$\sembrack{\cdot}^*$ for its fixed-point closure. To avoid duplicating identical
rules across mutable and immutable containers, we write $K \in \{\mathtt{Array},
\mathtt{Vector}\}$ for a container family and $\kappa_K \in \{\mathtt{array},
\mathtt{vector}\}$ for its corresponding type constructor (with $\kappa$
ranging over $\{\mathtt{array}, \mathtt{vector}\}$). In a block body,
$(S_j)_{j=1}^{k}$ denotes the concatenation $S_1 \cdots S_k$ of the statement
sequences $S_j$, and inline integer expressions such as $n \cdot k$, $n' / k$,
and $i \cdot k + (j - 1)$ in operand positions abbreviate the corresponding
\texttt{Word32} arithmetic \texttt{prim} bindings.

\section{Limitations}
As outlined above, this implementation only supports the case when all AoP
containers of a given type are flattened -- we cannot support a mix of flattened
and unflattened AoP containers with a given type using the strategy above. The
implementation discussed in this document simply emits an error if it encounters
an un-flattenable construct, none of which appear in the benchmark suites that
we evaluated this optimization against.

It is debatable whether supporting a fallback is required for the transformation
to be usable by real developers. The problem to worry about is that the
AoP->AoS/SoA transformation breaks pointer equality for array elements, i.e. for
an SML program like:
\begin{minted}{sml}
  val arr : (int * int) array = Array.array (3, (0, 0))
  val element = (1, 2)
  val _ = Array.update (arr, 1, element)
  val element' = Array.sub (arr, 1)
\end{minted}
Are \texttt{element} and \texttt{element'} physically identical? If this element
is \texttt{ShallowFlatten}ed, the answer is ``no:'' we cannot preserve pointer
equality, since the write/read result in pack/unpack operations that construct a
new tuple. From the perspective of strict StandardML as defined in the language
specification \citet{sml-def}, this is a non-issue: there is no way to observe
pointer equality of tuples in the source language, and so the compiler has
complete freedom. The only spec-compliant way to write this test would be to
wrap the element type in \texttt{ref}:
\begin{minted}{sml}
  val arr : (int * int) ref array = Array.array (3, ref (0, 0))
  val element = ref (1, 2)
  val _ = Array.update (arr, 1, element)
  val element' = Array.sub (arr, 1)
\end{minted}
Now we are guaranteed that \texttt{element = element'} holds, which is preserved
by \texttt{PreFlatten}.

However, both MLton and MPL extend the source language with constructs that
allow user programs to observe this behavior: both have \texttt{MLton.eq}
(physical equality for arbitrary values), and MPL additionally offers
compare-and-swap primitives to support implementing lock-free parallel
algorithms.

Since physical equality of tuples is not defined in \citet{sml-def}, one option
to resolve the issue would be to simply allow \texttt{MLton.eq}/compare-and-swap
to return \texttt{false} in these cases. Another simple option would to be
disable \texttt{ShallowFlatten} for all values of any types that participate in
one of the forbidden comparisons (i.e. a \texttt{MLton.eq} applied to an
\texttt{int * int} tuple anywhere in the program disables
\texttt{ShallowFlatten} for all containers of \texttt{int * int}), perhaps
refined by a dataflow analysis to determine if the elements in the forbidden
comparison may have originated in a container.

This results in a potentially-unpleasant performance cliff for users, but there
are various simple workarounds -- e.g. users can wrap any objects that must be
tested for pointer equality in \texttt{ref} cells (which are not impacted by
\texttt{ShallowFlatten}).
