The action of the \texttt{ShallowFlatten} pass is to eliminate array-of-tuple
types from the program, converting them to either a single flat array or a tuple
of arrays. It is intended to be a more ``aggressive'' extension of the existing
\texttt{DeepFlatten} pass, extending to cases where temporary tuple allocations
are required.

\section{Motivation}
As outlined in \cref{sec:background_deep_flatten}, the MLton default
array-of-pointers layout is hostile to the design of modern CPU caches,
introducing a load to an unpredictable, likely-cold heap location on every
element access. The existing remedy to this problem is the \texttt{DeepFlatten}
pass, but \texttt{DeepFlatten} only supports the case where the transformation
is completely ``free,'' introducing zero new \texttt{tuple} allocations. From
the perspective of performance, this seems to be an inversion of
priorities: \texttt{ShallowFlatten} takes the opposite approach, inserting
temporary \texttt{tuple} objects for all operations into or out of containers
and relying on later optimization passes to eliminate them when possible.

%% What alternatives to \texttt{DeepFlatten} could we design?

Simply modifying the existing \texttt{DeepFlatten} pass to insert new
allocations is potentially flawed: \texttt{DeepFlatten} needs to act on an IR
that can express the ``container of flattened values'' notion
of \cref{fig:flatten_generated_c}. The MLton compilation pipeline does not
introduce this affordance until after \texttt{SSA} -- therefore
(since \texttt{Flatten} targets \texttt{SSA}), we may fail to optimize away new
allocations that could have been elided by \texttt{Flatten}. As a solution,
we \texttt{ShallowFlatten} targets the \texttt{SSA} IR, and run it before
plain \texttt{Flatten}. The name \texttt{ShallowFlatten} is intended to contrast
with \texttt{DeepFlatten}, conveying an idea that we do not ``reach inside'' the
representation of the container type.

These two representation choices correspond to the familiar

natural default for a C++ programmer, where a composite type is embedded

contiguous chunks of data into vector registers (\cref{fig:cpp_soa_diagram}). The
MLton default array-of-pointers layout (\cref{fig:aop_example}) lacks a name in
standard performance-engineering parlance -- we will refer to it here as ``AoP''
for simplicity.

Bridging the gap consists, broadly, in inserting ``pack'' and ``unpack''
sequences as necessary around all \texttt{prim} operations that access container
types, replacing the AoP container type with its AoS/SoA equivalent, and
rewriting the container \texttt{prim}s appropriately
(\cref{fig:pack_unpack_example}). This allows us to preserve all of the
pre-existing names and (non-container) types in the consuming code, at the cost
of potentially unnecessary tuple allocations.

Running in \texttt{SSA} allows us to leverage existing \texttt{Flatten}
machinery to eliminate these temporary tuples, in exchange for which we
sacrifice the ability to express the notion of ``\texttt{tuple} elements
embedded into an array'' that \texttt{DeepFlatten} relies on. However, for
containers of homogeneous tuples, this level of control is unnecessary -- any
AoP container of length $n$ over a homogeneous-type tuple \texttt{(a * a * \dots
* a)} on $k$ elements can be converted into an AoS container of length $nk$. For
the benchmarks explored below, accepting this restriction does not sacrifice any
performance -- container-of-tuple types represented in these workloads generally
correspond to e.g. 2-$d$ points in space, which are naturally homogeneous. To
ensure fair benchmarks, the implementation of \texttt{ShallowFlatten} applies
the homogenous type restriction to both the AoS and the SoA transformations.

While inserting pack/unpack operations allows us to preserve pre-existing names
and types in code that consumes container elements, the types of the containers
themselves must be rewritten in order to reflect the new layouts. Like
\texttt{PreFlatten} (and unlike \texttt{DeepFlatten}), \texttt{ShallowFlatten}
aims to be a simple, purely-local transformation (rather than a complicated
global lattice analysis). Consequently, it is necessary for the pass to
eliminate every single appearance of a flattenable container type -- even those
embedded inside of e.g. \texttt{datatype} definitions or other container types
-- since otherwise we would end up with mismatched types at boundaries where
flattenable containers are embedded inside of other objects. See
\cref{fig:soa_flat_deep_example} for an illustration.

Finally, we consider the cases when this transformation is most likely to be
profitable: since we are concerned with efficiently utilizing memory bandwidth,
this transformation makes the most sense when the size of the \texttt{tuple}
member is small -- in the limiting case, an array with elements that are many-KB
large has little to gain from the AoP to AoS/SoA conversion. Hence we limit the
transformation to apply only to tuples below a certain size threshold (measured
in the count of members, for simplicity).

\section{Implementation}
We will formalize the action of the pass in three steps: first, a
``flavor''-independent high level structure, parameterized on a ``flavor''
$\Phi \in \{\Phi_\texttt{AoS}, \Phi_\texttt{SoA}\}$; second, we describe the
flavor-dependent transformation on types, and finally the flavor-dependent
transformation on statements.

We define the flavor-dependent ``\texttt{tuple} width'' of a type $t$ as
$w_t^\Phi(t)$, where:
\[
w_t^{\Phi_{\texttt{SoA}}}(t) =
\begin{cases}
n &: \textrm{if $t$ is of the form $\tau_1 * \cdots * \tau_n$} \\
0 &: \textrm{otherwise}
\end{cases}
\qquad
w_t^{\Phi_{\texttt{AoS}}}(t) =
\begin{cases}
n &: \textrm{if $t$ is of the form $\underbrace{\tau * \cdots * \tau}_{n}$} \\
0 &: \textrm{otherwise}
\end{cases}
\]
We likewise define the ``container width'' of a type $c$ as $w_c^\Phi(c)$, where:
\[
w_c^\Phi(c) =
\begin{cases}
w_t^\Phi(t) &: \textrm{if $c$ is $t$ \texttt{array} or $t$ \texttt{vector}} \\
0 &: \textrm{otherwise}
\end{cases}
\]
In the context of \texttt{ShallowFlatten} We say that a type $\tau$ is
``flattenable'' under flavor $\Phi$ if:
\[
2 \leq w_c^\Phi(\tau) \leq W
\]
where $W$ is some user-specified upper bound (selected to maximize performance).
Note that while $\Phi_{\texttt{SoA}}$ supports heterogeneous tuples directly,
our evaluation in \cref{ch:evaluation} configures both flavors with the
homogeneous-type policy so that AoS and SoA transform the same set of
containers.

We also partition \texttt{prim}s into ``flattenable'' and ``unflattenable:''
``flattenable'' \texttt{prim}s are those that manipulate \texttt{array}
or \texttt{vector} types; all other \texttt{prim}s are ``unflattenable.''

Then, at a high level, the action of the pass is:
\begin{itemize}
\item Visit all non-\texttt{statement}s; recursively
(i.e. traversing nested types) and iteratively (i.e. repeating until
convergence) transform all \texttt{type}s under the flavor $\Phi$.

\item Visit all \texttt{statement}s: iteratively transform under $\Phi$ until convergence.
For \texttt{statement}s that contain a flattenable \texttt{prim}, this means
rewriting the \texttt{prim} according to $\Phi$; for statements that do not
contain a flattenable \texttt{prim}, it means transforming only \texttt{type}s.

\end{itemize}

See \cref{fig:shallow_flat_toplevel} for a formalization of this process -- the
overall action of the pass is the fixed-point $\sembrack{P}_\phi^*$.

\section{Limitations}
As outlined above, this implementation only supports the case when all AoP
containers of a given type are flattened -- we cannot support a mix of flattened
and unflattened AoP containers with a given type using the strategy above. The
implementation discussed in this document simply emits an error if it encounters
an unflattenable construct, none of which appear in the benchmark suites that
we evaluated this optimization against.

The primary case when such a fallback would be necessary is when the source
program contains a construct that can observe physical equality
between \texttt{tuple} elements (or lack thereof). For a motivating example,
consider the case when a \texttt{tuple} element round-trips through an array, as
in \cref{fig:push_pop}. At the end of this sequence, are \texttt{element}
and \texttt{element'} physically identical?

If \texttt{arr} has been \texttt{ShallowFlatten}ed, the answer is ``no:'' we
cannot preserve pointer equality, since the write/read result in pack/unpack
operations that construct a new tuple. From the perspective of strict Standard ML
as defined in the language specification \citep{sml-def}, this is a non-issue:
there is no way to observe pointer equality of tuples in the source language,
and so the compiler has complete freedom. The only language-extension-free way
to write this test would be to wrap the element type in \texttt{ref}, as
depicted in \cref{fig:push_pop_ref} -- in which case we are guaranteed
that \texttt{element = element'}, which is preserved by \texttt{PreFlatten}.

However, both MLton and MPL extend the source language with constructs that
allow user programs to observe this behavior: both have \texttt{MLton.eq}
(physical equality for arbitrary values), and MPL additionally offers
compare-and-swap primitives to support implementing lock-free parallel
algorithms.

Since physical equality of tuples is not defined by \citet{sml-def}, one option
to resolve the issue would be to simply allow \texttt{MLton.eq}/compare-and-swap
to (perhaps spuriously) return \texttt{false} in these cases. Another simple
option would to be disable \texttt{ShallowFlatten} for all values of any types
that participate in one of the forbidden comparisons (i.e. a \texttt{MLton.eq}
applied to an
\texttt{int * int} tuple anywhere in the program disables
\texttt{ShallowFlatten} for all containers of \texttt{int * int}), perhaps
refined by a dataflow analysis to determine if the elements in the forbidden
comparison may have originated in a container. This results in a
potentially-unpleasant performance cliff for users, but there are various simple
workarounds -- e.g. users can wrap any objects that must be tested for pointer
equality in \texttt{ref} cells, as described above.

Another approach would be to redefine \texttt{MLton.eq} and the MPL array CaS
primitives to forbid tuple arguments: this would mirror, for example, the Java
language ``value classes'' proposal of \citet{jep401-valhalla}, redefining all
SML source-language tuples as ``value objects'' in the sense of that proposal,
and completely restricting the notion of physical equality to \texttt{ref}
cells. Given that the value-to-ref rewrite is trivial and no examples of, this
seems to impose minimal programmer burden and win substanial flexibility for the
compiler.

An additional limitation that is specific to the AoS flavor, as described above,
is the restriction to tuples of uniform types. This is an intentional tradeoff
for the sake of exploration, allowing us to better-leverage the
existing \texttt{Flatten} pass without a substanial re-architecture of the
compiler -- the \texttt{SSA} IR today is insufficiently-expressive to implement
the AoS transformation. Future work could remove this restriction by
extending \texttt{SSA} as necessary, or by re-implementing \texttt{Flatten} to
run (again, perhaps) in later stages of the compilation pipeline.
