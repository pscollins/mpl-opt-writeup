\paragraph{Overview}

In the source language, Standard ML offers the programmer no direct control over
the memory layout for data structures in the generated code: consequently, it is
the compiler's responsibility to choose a memory layout that efficiently
utilizes the hardware of the target platform. However, the most ``literal''
translation of the source language to machine code (i.e. the one which preserves
exactly the data structures present in the user's original input) has
disastrous performance characteristics on modern CPUs: every function call and
every access into a (non-primitive) container incurs a cache miss at an
unpredictable address in the heap.

Each Standard ML compiler chooses different strategies to mitigate these costs:
MLton \citep{mlton-website} deploys a class of optimizations that it calls
``flattening,'' first introduced by \citet{flat-paper}. These strategies are
also used in MLton's parallel-friendly fork, MaPLe (MPL), introduced
by \citet{mpl-orig}.

In this document, we will explore two novel ``flattening'' strategies: the
first, \texttt{PreFlatten} (building on top of the existing \texttt{Flatten}
pass from \citet{flat-paper}), specializes functions in order to enable
more-aggressive elimination of heap allocations at callsites. The second,
\texttt{ShallowFlatten} (building on top of the existing \texttt{DeepFlatten}
pass) transforms layouts of containers in order to eliminate pointers.

Our \texttt{PreFlatten} pass implements two distinct concrete optimizations,
which we benchmark and analyze separately. The high-level goal of the pass is to
pull ``pack'' operations (i.e. object constructor calls, corresponding to
potential heap allocations) across function call boundaries, enabling subsequent
optimization passes to eliminate the constructed object completely (in some
cases). The two concrete optimizations target two of the languages' object
types: \texttt{tuple} aggregates and tagged-union \texttt{datatype} values.

In order to achieve this goal, the pass emits a duplicate definitions of the
callee that are specialized to the particular patterns of ``pack'' operations
that immediately precede calls. For \texttt{tuple} pack operations, this is
necessary in order to handle cases where different callers exhibit different
patterns; for \texttt{datatype} pack operations, it is required in order to pass
the union's payload separately from the ``tag.''

These specialized definitions interact with MLton's downstream \texttt{Chunkify}
pass (which partitions the generated C code across multiple C functions in order
to control compile times), perturbing chunk boundaries by virtue of increased
binary size. We find that in practice, this effect is large enough to nullify
any potential wins from \texttt{PreFlatten}: most benchmark configurations show
a loss (on the order of a 1\% geomean latency increase across all impacted
benchmarks, generally driven by a handful of large outlier regressions). After
controlling for the effect of the \texttt{Chunkify} heuristic (by forcing all
generated code into a single chunk), the \texttt{PreFlatten} optimizations are
neutral-to-positive, demonstrating a geomean latency reduction on the order of
1-2\% across most impacted benchmarks. This suggests that the \texttt{Chunkify}
heuristic may be over-tuned to the existing benchmark suite.

Our \texttt{ShallowFlatten} pass, likewise, explores two distinct \hl{concrete}
optimizations, which we benchmark and analyze separately. For both
optimizations, we rewrite containers over tuple types so that the ``innermost''
type is no longer a \texttt{tuple}, and hence no longer requires an indirection
to access. Our first strategy replaces an array-of-tuple with a tuple-of-array
(i.e. replacing a \texttt{($\tau_1$ * $\tau_2$) array} by a \texttt{$\tau_1$
array * $\tau_2$ array}), achieving a layout analogous to the HPC-standard
struct-of-array (SoA) \hl{layout}. Our second strategy replaces an
array-of-homogeneous-tuple with a flattened array whose primitive members are
allocated inline (i.e. replacing a \texttt{($\tau$ * $\tau$) array} of length
$n$ by a \texttt{$\tau$ array} of length $2n$), achieving a layout analogous to
standard the C/C++ array-of-struct (AoS). The \texttt{ShallowFlatten} pass is a
close sibling to the existing \texttt{DeepFlatten} pass, but it differs from it
by: 1) optimizing layouts even in cases where coercions are required, 2)
targetting an early, high-level IR so as to better-leverage existing
optimization passes, and 3) supporting an SoA layout in addition to SoA.


Evaluations show that both \texttt{ShallowFlatten} transformations are
overwhelmingly positive in the single-threaded case, demonstrating latency
reductions on individual benchmarks as large as 50\% (i.e. 2x speedups) and
geomean latency reductions on the order of 10\% across impacted benchmarks
within a particular suite. Multithreaded benchmarks show mixed results that
appear to indicate a bad interaction with MPL's garbage collection heuristics:
controlling for this effect by forcing a synchronous GC pause at the beginning
of each benchmark iteration produces latency reductions on individual benchmarks
as large as 90\% (i.e. 10x speeups) and suite-geomean latency reductions of
50\%.

\paragraph{Contributions}

\begin{itemize}
\item The design and implementation of the \texttt{PreFlatten} pass for MLton and MPL,
which aim to eliminate indirections around function call boundaries.

\item The design and implementation of the \texttt{ShallowFlatten} pass for MLton
and MPL, which aim to eliminate indiractions around containers.

\item An empirical evaluation of the two new passes across both MLton and MPL,
with a detailed investigation of their interactions with existing system
components and sources of noise.
