The action of the \texttt{PreFlatten} transformation is to ``push
down'' \texttt{tuple} and \texttt{datatype} constructor calls across function
call boundaries, creating new opportunities for subsequent optimization passes
to eliminate the corresponding allocations entirely. It is intended to be a more
``agressive'' extension of the existing \texttt{Flatten} pass, supporting a
mixture of flattenable and un-flattenable callsites by duplicating function
definitions.

\section{Motivation}
The basic intuition is: whenever a \texttt{tuple} allocation feeds directly into
a function call, we can eliminate the \texttt{tuple} from the function signature
by moving the allocation from the caller to the callee (depicted
in \cref{fig:pre_flatten_example}). So long as the arguments to the flattened
function can pass in registers, this should be no-more-expensive than the
original call; we have simply delayed copying the tuple members from registers
into memory.

For a given \texttt{(argument, function call)} pair, we say that the pair is
``flattenable'' if it is in the form depicted in \cref{fig:pre_flatten_example},
i.e. if the argument is the direct result of a \texttt{tuple} constructor call.
In a flattenable pair, the argument is a candidate to be ``pushed down'' across
the function boundary so as to elide the allocation.

In the case that all concrete arguments across all callsites to a given formal
function parameter are flattenable, then it is sufficient to replace the
existing non-flat function defintion with a new, flattened function definition.
In order to support a mixture of flattenable and unflattenable calls to a given
function definition, however, we must emit duplicate definitions of the
function, each specialized to a particular flattening decision at some caller
(\cref{fig:pre_flatten_example_dup}).

This strategy also naturally extends to eliminating \texttt{ConApp}s, as
depicted in \cref{fig:pre_flatten_example_con}: if the argument at some callsite
is the direct result of a a \texttt{datatype} object allocation, we can emit a
new definition of the callee that is specialized to the statically-known case in
the caller and ``push down'' the \texttt{ConApp} from caller to callee. After
the ``push down'' step, we can rely on existing optimization patterns to
eliminate now-dead blocks corresponding to cases that are no longer reachable in
the specialized function. For \texttt{ConApp} calls corresponding to closure
environments, this transformation subsumes the action of
the \texttt{Polyvariance} pass described in \cref{sec:background_polyvar}.

\begin{itemize}
\item \texttt{Simplify}: when a \texttt{tuple} ``pack'' operation is pushed
all the way down into the same function as a corresponding ``unpack''

\item \texttt{KnownCase}: when a \texttt{ConApp} constructor call is pushed all
the way down to the \texttt{case} statement that consumes it, \texttt{KnownCase}
replaces the \texttt{case} statement with a static \texttt{jump}
(\cref{fig:simplify_known_case}).

\item \texttt{Flatten}: if \texttt{PreFlateen} runs before \texttt{Flatten}, then
it can create new opportunities for \texttt{Flatten} by creating larger
subgraphs of the dataflow graph that are free from un-flattenable constructs
(such as \texttt{ConApp} calls -- \cref{fig:simplify_enable_flatten})

\end{itemize}

In the experiments described in \cref{sec:results}, we run
the \texttt{ConApp}-flattening configuration before \texttt{Flatten} and

Finally, we note one source of complexity in flattening recursive function
calls: consider, for example, a function that recursively acts on
a \texttt{tuple} argument, as depicted in \cref{fig:rec_func_sml_ssa}. In this
case, phrasing our transformation as a strictly-local peephole optimization has
a fundamental limitation: we can never flatten the recursive call inside of a
flattened specialization (\cref{fig:bad_flat_rec_func_ssa}). In order to fix
this issue, it is necessary to iteratively apply the transformation to the
emitted specializations, so that a flattenable call within the flattened
specialization can call itself rather than the original function.
See \cref{fig:good_flat_rec_func_ssa} for an example.

\section{Implementation}
We separate the action of the pass into two (interleaved) phases: first,
analysis; second, transformation. The analysis phase differs
between \texttt{tuple} flattening and \texttt{ConApp} flattening, while the
transformation phase is shared.

In the analysis phase, our goal is to construct a mapping $\sigma$ from function
calls to their per-argument flattening decisions: as a first pass, we simply
examine each callsite to record whether each argument is ``flattenable''. For
the \texttt{tuple} analysis, an argument is flattenable
(written \texttt{Flatten}) if it is the direct result of a \texttt{tuple}
constructor call; for the \texttt{ConApp} analysis, an argument is flattenable
(written $\texttt{Flatten}_C$) if it is the direct result of a \texttt{con} $C$
constructor call. Unflattenable arguments are is marked \texttt{Preserve}. Call
the result of this analysis $\sigma_i$, the initial flattening decision.

For notational simplicity, we'll imagine that each \texttt{call} statement in
the program is tagged with a label \texttt{callN}, corresponding to its index in
the original program: the $\sigma_i$ resulting from some example programs is
depicted in \cref{fig:example_sigma_init}.

Next, we examine all \texttt{Flatten} and $\texttt{Flatten}_C$ decisions and
choose to ``downgrade'' a subset of them to \texttt{Preserve} based on cost
heuristics. The cost heuristics evaluated in this project are:

%% \hl{TODO: the MLton-MLton experiments are in the wrong configuration (all
%% unpack + global), try to revisit --- fixed}
\begin{itemize}
\item For \texttt{tuple} flattening: only flatten tail-recursive function calls.

\item For \texttt{ConApp} flattening: unconditionally flatten, no ``downgrade'' heuristics.
\end{itemize}

These heuristics are motivated by the MLton calling convention described
in \cref{sec:background_sml_ssa}: non-tail calls (if preserved until C code
generation) pass data through explicit stack operations, so
flattening \texttt{tuple} arguments to a non-tail corresponds to a true copy
rather than simply leaving data resident in registers across a call boundary.
Tail calls, by contrast, are more likely to pass data in registers. For
the \texttt{ConApp} case, no such tradeoff exists: flattening a \texttt{ConApp}
results in a \texttt{tuple} argument that is no-more-expensive to pass.

After applying these heuristics, we end up with a final analysis result,
$\sigma$. The action of $\sigma$ on the program is described
in \cref{fig:tuple_flattening_impl}, specifically:
\begin{itemize}

\item
First, we apply our analysis $\Sigma$ to the program in order
to arrive at a flattening decision $\sigma$ (described above),
\cref{fig:preflatten_analysis}.

\item For each caller \texttt{callN} of a function \texttt{f} whose
flattening decision $\vec{d} = \sigma(\texttt{f}, \texttt{callN})$ is
non-trivial (i.e.\ $\vec{d} \neq \texttt{Preserve}^n$), we emit a specialized
function $\texttt{f}_{\vec{d}}$ for that flattening decision
(reusing the duplicated definitions where
possible), \cref{fig:preflatten_emit_new}.

their old, unflattened names (by constructing a temporary \texttt{tuple}
or \texttt{datatype} object) and then jumps unconditionally to the original
entry block of the function, \cref{fig:preflatten_rebind_block}.


\item For each caller \texttt{callN} of a function \texttt{f},

allocation itself: \texttt{Flatten} passes the arguments to the \texttt{tuple} as a
flat sequence of variables, $\texttt{Flatten}_C$ passes the \texttt{ConApp}
payload as a \texttt{tuple}, \cref{fig:preflatten_fix_call}.

Thinking in terms of the structure of the overall data-flow graph, then, we can
say the following:

\begin{itemize}
\item For \texttt{Flatten}, since constraints ``flow forward''
along directed edges, the action of the pass is to identify a path through the
dataflow graph that is both tuple-valued and flattenable at each edge,
traversing inside function/block bodies. The transformation then rewrites the
type of each edge, leaving the structure of the dataflow graph unchanged.

\item For \texttt{PreFlatten}, we look at only single edges (rather than full paths),
and the action of the pass is to duplicate nodes in the dataflow graph, introducing
new, flat edges.

\end{itemize}

%% The two type flattening implementations share a common framework, differing only
%% in the types of operations that they match on:

%% \begin{enumerate}
%% \item Find all \texttt{call} statements with a ``pack'' operation that feeds
%%   directly into a \texttt{call}: for the \texttt{tuple} case, this corresponds
%%   to \texttt{tuple} constructor applications:
%% \begin{minted}{python}
%%   t: a * b * ... = tuple(x1, x2, ...)
%%   call bbN f_tuple(t, y, z, ...) # call1
%%   # ...
%%   def f_tuple(t: a * b * ..., y: c, z: d, ...) -> ...:
%% \end{minted}
%% and for the \texttt{datatype} case, this corresponds to \texttt{ConApp}s:
%% \begin{minted}{python}
%%   datatype ConType = Con1 of a * b * ... | Con2 of ...
%%   # ...
%%   t: a * b * ... = ...
%%   # ...
%%   c: ConType = con Con1(t)
%%   call bbN f_con(c, y, z, ...) # call2
%%   # ...
%%   def f_con(c: ConType, y: c, z: d, ...) -> ...:
%% \end{minted}
%% \item Tag each such \texttt{call} statement with a per-argument flattening
%%   decision, to indicate which arguments are valid targets to flatten, and
%%   associate the tagged \texttt{call}s with their callee. For the flattenable
%%   arguments, we include the information necessary to construct the flattened
%%   call (i.e. the arguments to the \texttt{tuple} / \texttt{ConApp} call).
%%   Continuing the examples from above, we would have:
%% \begin{minted}{python}
%%     f_tuple_caller_info = {
%%       'call1': [FlattenVar(x1, x1, ...), PreserveVar, PreserveVar, ...]
%%       # ...other callers...
%%     }
%%     f_con_caller_info = {
%%       'call2': [FlattenVar(t), PreserveVar, PreserveVar, ...]
%%       # ...other callers...
%%     }
%% \end{minted}
%% \item Traverse all function-callee-decision collections and apply heuristics to
%%   ``downgrade'' \texttt{FlattenVar} decisions to \texttt{PreserveVar} decisions
%%   when specialization would be unprofitable.

%% \item Traverse all function-callee-decision collections and emit the new
%%   required specialized versions: an all-\texttt{PreserveVar} decision
%%   corresponds to the original function. Any \texttt{FlattenVar(...)} decisions
%%   result in a new specialization whose formal parameters include the flat
%%   arguments in the appropriate location, and whose first block re-binds the
%%   flattened names to the old, un-flattened name before jumping to the original
%%   first block. That is, for the \texttt{tuple} example above, we emit:
%% \begin{minted}{python}
%%   # Specialization for [FlattenVar(...), PreserveVar, ...]
%%   def f_tuple_flat0(x1: a, x2: b, ..., y: c, z: d, ...) -> ...:
%%     block bbBind():
%%       # Re-introduce the original, unflattened name
%%       t: a * b * ... = tuple(x1, x2, ...)
%%       # Jump to the original first block
%%       goto bb0()
%% \end{minted}
%% and for the \texttt{ConApp} example, we emit:
%% \begin{minted}{python}
%%   # Specialization for [FlattenVar(...), PreserveVar, ...]
%%   def f_con_flat0(t: a * b * ..., ..., y: c, z: d, ...) -> ...:
%%     block bbBind():
%%       # Re-introduce the original, unflattened name
%%       c: ConType = con Con1(t)
%%       # Jump to the original first block
%%       goto bb0()
%% \end{minted}

%% \item Traverse the program to visit all \texttt{call} statements again, and
%%   redirect the call target to the appropriate specialization that we identified
%%   in the previous step (perhaps the original function). For non-identity
%%   flattening decisions, use the contents of the \texttt{FlattenVar(...)}
%%   argument to construct the appropriate flat call, i.e. for \texttt{tuple}:
%% \begin{minted}{python}
%%   t: a * b * ... = tuple(x1, x2, ...)
%%   call bbN f_tuple(t, y, z, ...) # call1
%% \end{minted}
%% becomes:
%% \begin{minted}{python}
%%   call bbN f_tuple_flat0(x1, x2, ..., y, z, ...)
%% \end{minted}
%% and for \texttt{ConApp}, 
%% \begin{minted}{python}
%%   c: ConType = con Con1(t)
%%   call bbN f_con(c, y, z, ...) # call2
%% \end{minted}
%% becomes:
%% \begin{minted}{python}
%%   call bbN f_con_flat0(t, y, z, ...)
%% \end{minted}

%% \item With the callsite-flattening mapping still intact and with the duplicated
%%   functions retaining the original variable names, iteratively re-apply the
%%   process above on all newly-emitted functions until either convergence or a
%%   user-specified iteration limit is reached. This fixes an issue with (mutually)
%%   recursive functions, where a collection of $n$ mutually recursive calls
%%   require $n$ iterations to remove unnecessary pack/unpack operations, e.g. for
%%   a source program like:
%% \begin{minted}{python}
%%   f(...) -> ...:
%%     # ...
%%     # flat call to `g`
%%     t0: a * b = (x, y)
%%     call bbN g(t0)

%%   g(t: a * b) -> ...:
%%     # ...
%%     block bbM():
%%       # arguments for recursive call
%%       t2: a * b = (w, z)
%%       call bbK g(t2)
%% \end{minted}
%% The action of the pass is as follows: for both the call in \texttt{f} and
%% \texttt{g}, we can flatten the function argument, and so we emit a new
%% specialization of the function, \texttt{g\_flat}
%% \begin{minted}{python}
%%   f(...) -> ...:
%%     # ...
%%     # flat call to `g`
%%     t0: a * b = (x, y)
%%     call bbN g_flat(x, y)  # pointed to flat specialization

%%   g(t: a * b) -> ...:
