The core \texttt{PreFlatten} transformation is to duplicate function bodies so
that callers can avoid unnecessary pack/unpack sequences, eliding
either \texttt{tuple} constructors or \texttt{ConApp} calls. It is intended to
be a generalization of the existing \texttt{Flatten} pass in order to handle the
case where the lattice-based analysis chooses not to flatten based on a mixture
of flattenable and un-flattenable callers.

\section{Motivation}
The basic intiution is that we can use a simple peephole optimization to ``push
together'' tuple pack/unpack operations separated by function call boundaries
(as depicted in \cref{fig:pre_flatten_example}), and then rely on existing
optimizations to elide the temporary tuple.

\begin{figure}[htbp]
  \centering
  \begin{subfigure}[t]{0.48\textwidth}
    \caption{Before \texttt{PreFlatten}}
    \label{fig:pre_flatten_before}
    \vspace{1mm}
\begin{minted}[fontsize=\scriptsize,frame=single,framesep=2mm,rulecolor=\color{black!20}]{python}
def f(...) -> ...:
  # ...other blocks...

  block bbN():
    t: a * b = tuple(x0, x1)
    # call g(t) and return to bbM
    call bbM g(t)

  # ...other blocks...

def g(t: a * b) -> ...:
  block bb0():
    x0: a = select(t, 0)
    x1: b = select(t, 1)
    # ...etc...

  # ...other blocks...
\end{minted}
  \end{subfigure}\hfill
  \begin{subfigure}[t]{0.48\textwidth}
    \caption{After \texttt{PreFlatten}}
    \label{fig:pre_flatten_after}
    \vspace{1mm}
\begin{minted}[fontsize=\scriptsize,frame=single,framesep=2mm,rulecolor=\color{black!20}]{python}
def f(...) -> ...:
  # ...other blocks...

  block bbN():
    # call g(x0, x1) and return to bbM
    call bbM g_flat(x0, x1)

  # ...other blocks...

def g_flat(x0_flat: a, x1_flat: b) -> ...:
  block bb0():
    t: a * b = tuple(x0_flat, x1_flat)
    x0: a = select(t, 0)
    x1: b = select(t, 1)
    # ...etc...

  # ...other blocks...
\end{minted}
  \end{subfigure}
  \caption{The \texttt{PreFlatten} transformation duplicates and specializes the callee to accept unpacked arguments, pushing tuple construction across the function call boundary.}
  \label{fig:pre_flatten_example}
\end{figure}

For a given \texttt{(argument, function call)} pair, we say that the pair is
``flattenable'' if it is in the form depicted in \cref{fig:pre_flatten_example},
i.e. if the argument is the direct result of a \texttt{tuple} constructor call.
In a flattenable pair, the argument is a candidate to be ``pushed down'' across
the function boundary so as to elide the allocation.

In the case that all concrete arguments to a given formal function parameter are
flattenable, then it is sufficient to replace the existing non-flat function
defintion with a new, flattened function definition, but in order to support a
mixture of flattenable and unflattenable calls to a given function definition,
we must emit duplicate definitions of the function to support
each \hl{flattening pattern}, as depicted in \cref{fig:pre_flatten_example_dup}.

\begin{figure}[htbp]
  \centering
  \begin{subfigure}[t]{0.48\textwidth}
    \caption{Before \texttt{PreFlatten}}
    \label{fig:pre_flatten_dup_before}

    call bbM g(t1)

  # ...as above...

\begin{minted}[fontsize=\scriptsize,frame=single,framesep=2mm,rulecolor=\color{black!20}]{python}

By iteratively applying this strategy, we can ``push together'' distant pairs of
flatten/unflatten operations, and so try to ensure that the maximum possible
number of callsites in the program are flattened -- even in cases where the
global \texttt{Flatten} transformation would fail.

This strategy also naturally extends to eliminating \texttt{ConApp}s, as
depicted in \cref{fig:pre_flatten_example_con}: given a callsite with a
constructor call, we emit a new definition of the callee that is specialized to
the statically-known case in the caller and ``push down'' the \texttt{ConApp}
from caller to callee. After the ``push down'' step, we can rely on existing
optimization patterns to eliminate now-dead blocks corresponding to cases that
are no longer reachable in the specialized function. For \texttt{ConApp} calls
corresponding to closure environments, this transformation subsumes the action of
the \texttt{Polyvariance} pass described in \cref{sec:background_polyvar}.

The two type flattening implementations share a common framework, differing only

\item Tag each such \texttt{call} statement with a per-argument flattening

  each $d_i$ indicates whether to preserve the argument (\texttt{PreserveVar}) or
  flatten it (\texttt{FlattenVar}). For the flattenable arguments, we include the
  information necessary to construct the flattened call (i.e. the arguments to
  the \texttt{tuple} / \texttt{ConApp} call). Continuing the examples from above,

\item Traverse all function-callee-decision collections and apply heuristics to
  ``downgrade'' \texttt{FlattenVar} decisions to \texttt{PreserveVar} decisions
  when specialization would be unprofitable.

\item Traverse all function-callee-decision collections and emit the new
  required specialized versions: an all-\texttt{PreserveVar} decision
  corresponds to the original function. Any \texttt{FlattenVar(...)} decisions
  result in a new specialization whose formal parameters include the flat
  arguments in the appropriate location, and whose first block re-binds the
  flattened names to the old, un-flattened name before jumping to the original
  first block. We express this AST transformation on a function definition
  $\texttt{def } f(\vec{p}) \mathbin{:} \tau_{\text{ret}} \mathrel{=} \vec{B}$
  under specialization decision $\sigma = (d_1, \dots, d_k)$ as:
  \[
    \trans[\sigma]{\texttt{def } f(p_1 \mathbin{:} \tau_1, \dots, p_k \mathbin{:} \tau_k) \mathbin{:} \tau_{\text{ret}} \mathrel{=} \vec{B}}
    = \texttt{def } f_\sigma(\vec{p}') \mathbin{:} \tau_{\text{ret}} \mathrel{=} B_{\text{bind}} \; \vec{B}
  \]
  where $\vec{p}' = (\trans[d_1]{p_1 \mathbin{:} \tau_1}, \dots, \trans[d_k]{p_k \mathbin{:} \tau_k})$,
  and $B_{\text{bind}} = \texttt{block } bbBind()$ is a fresh entry block preceding
  the original blocks $\vec{B} = (bb0, \dots)$. For each parameter $p_i \mathbin{:} \tau_i$
  and decision $d_i$:
  \begin{itemize}
  \item If $d_i = \texttt{PreserveVar}$, the formal parameter is unchanged: $\trans[d_i]{p_i \mathbin{:} \tau_i} = p_i \mathbin{:} \tau_i$, and no re-binding statement is needed in $B_{\text{bind}}$.
  \item If $d_i = \texttt{FlattenVar}(x_1, \dots, x_m)$ for a tuple type $\tau_i = \tau_{i,1} * \dots * \tau_{i,m}$, then $\trans[d_i]{p_i \mathbin{:} \tau_i} = x_1 \mathbin{:} \tau_{i,1}, \dots, x_m \mathbin{:} \tau_{i,m}$, and $B_{\text{bind}}$ includes the re-binding statement $p_i \mathbin{:} \tau_i \mathrel{=} \texttt{tuple}(x_1, \dots, x_m)$.
  \item If $d_i = \texttt{FlattenVar}(t)$ for a constructor type $\tau_i = \text{ConType}$ with constructor $\texttt{Con1}$ carrying payload of type $\tau_t$, then $\trans[d_i]{p_i \mathbin{:} \tau_i} = t \mathbin{:} \tau_t$, and $B_{\text{bind}}$ includes the re-binding statement $p_i \mathbin{:} \tau_i \mathrel{=} \texttt{con } \texttt{Con1}(t)$.
  \end{itemize}
  The transfer in $B_{\text{bind}}$ is an unconditional jump $\texttt{goto } bb0()$ to the original entry block.
  When $\sigma$ consists entirely of \texttt{PreserveVar} decisions, $\trans[\sigma]{\texttt{def } f \dots} = \texttt{def } f \dots$ (the function is left untouched).
  That is, for the running examples above, the pass emits the specialized definitions shown in \cref{fig:preflatten_specializations}: \cref{fig:preflatten_spec_tuple} for the \texttt{tuple} case and \cref{fig:preflatten_spec_con} for the \texttt{ConApp} case.

\item Traverse the program to visit all \texttt{call} statements again, and
  redirect the call target to the appropriate specialization that we identified
  in the previous step (perhaps the original function). We express the AST
  transformation on \texttt{call} transfers under analysis decision
  $\sigma = (d_1, \dots, d_k)$ as:
  \[
    \trans[\sigma]{\texttt{call } bbN \; f(a_1, \dots, a_k)} =
    \texttt{call } bbN \; f_\sigma(\trans[d_1]{a_1}, \dots, \trans[d_k]{a_k})
  \]
  where $f_\sigma$ is the target specialization (with $f_\sigma = f$ if all decisions
  are \texttt{PreserveVar}), and each argument $a_i$ is rewritten according to $d_i$:
  \[
    \trans[d_i]{a_i} =
    \begin{cases}
      a_i & \text{if } d_i = \texttt{PreserveVar} \\
      x_1, \dots, x_m & \text{if } d_i = \texttt{FlattenVar}(x_1, \dots, x_m) \\
      t & \text{if } d_i = \texttt{FlattenVar}(t)
    \end{cases}
  \]
  For non-identity flattening decisions, the contents of the \texttt{FlattenVar(...)}
  decision construct the appropriate flat call. Specifically, for \texttt{tuple}:
  \[
    \trans[\sigma]{\texttt{call } bbN \; f_{\text{tuple}}(t, y, z, \dots)} =
    \texttt{call } bbN \; f_{\text{tuple\_flat0}}(x_1, x_2, \dots, y, z, \dots)
  \]
  where $\sigma = (\texttt{FlattenVar}(x_1, x_2, \dots), \texttt{PreserveVar}, \texttt{PreserveVar}, \dots)$
  and $t \mathrel{=} \texttt{tuple}(x_1, x_2, \dots)$; and for \texttt{ConApp}:
  \[
    \trans[\sigma]{\texttt{call } bbN \; f_{\text{con}}(c, y, z, \dots)} =
    \texttt{call } bbN \; f_{\text{con\_flat0}}(t, y, z, \dots)
  \]
  where $\sigma = (\texttt{FlattenVar}(t), \texttt{PreserveVar}, \texttt{PreserveVar}, \dots)$
  and $c \mathrel{=} \texttt{con } Con1(t)$.

  user-specified iteration limit is reached. This fixes an issue with (mutually)
  recursive functions, where a collection of $n$ mutually recursive calls

\texttt{g}, we can flatten the function argument, and so we emit a new
specialization of the function, \texttt{g\_flat}, as shown in

applying the call transformation:
\[

\item Introduce fresh names for the symbols (specifically block labels and
  variable names) in all duplicated functions. This is a requirement from MLton,
  which expects that symbols' names are globally unique.

\item Signal either ``progress'' (if we emitted a new specialization) or
  ``done'' to the caller. Repeat until either convergence or a user-specified
  iteration limit is reached.
\end{enumerate}

\section{Limitations}
Note that the worst-case bloat in IR size is quadratic in a single iteration:
the very upper bound is that every statement in the program causes us to
duplicate the entire program. This is clearly problematic in practice, and it
interacts particularly poorly with chunkification (since flattened tuples can be
more expensive than non-flat tuples to pass across chunk boundaries, due to the
required stack writes that are linear in the number of tuple elements).
